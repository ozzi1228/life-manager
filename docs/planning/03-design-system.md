## 2. 테마 분석과 보완

### 2.1 Salesforce 테마의 성격

| 특징 | 값 | 화면 인상 |
|---|---|---|
| 기본색(primary) | 하늘빛 파랑 `oklch(0.6704 0.1369 235.29)` (≈ `#1B96E6` 계열) | 신뢰감 있는 업무 도구 느낌, 차분함 |
| 배경 | 거의 흰색에 아주 옅은 청색 `oklch(0.9898 0.0025 228.78)` | 눈부심이 적은 밝은 화면 |
| 카드 | 순백 `oklch(1 0 0)` | 배경과 미세한 차이로 카드가 떠 보임 |
| 모서리 | `--radius: 0.375rem` (6px) | 각진 편. 둥글둥글한 다이어리 앱보다 정돈된 인상 |
| 그림자 | 넓게 퍼지는 옅은 그림자 (blur 12px, 투명도 0.04~0.08) | 테두리보다 그림자로 층을 구분 |
| 기본 버튼 글자색 | 짙은 남색 `oklch(0.1613 0.0088 4.63)` (흰색 아님) | 파란 버튼 위 검은 글자. 명암비 확보 목적 |
| 차트 5색 | 파랑·남보라·청록·연보라·짙은 청록 | 같은 계열의 차분한 색. 범주 구분력은 낮음 |
| 다크 모드 | 짙은 청회색 배경 `oklch(0.1608 0.0053 219.81)`, 밝아진 파랑 `oklch(0.7706 0.1317 235.05)` | |

이 테마는 "차분한 생산성 도구 + 개인 다이어리"라는 기존 방향(ChatGPT 제안) 중 **생산성 도구 쪽**에 가깝다. 다이어리다운 따뜻함은 테마 색이 아니라 **펫, 목표 색상 팔레트, 표지·포스터 이미지, 일러스트 빈 화면**으로 채운다. [제안]

### 2.2 테마를 그대로 쓰면 생기는 문제와 보완 [제안]

테마의 색상 값은 바꾸지 않는다. 아래는 테마에 **없는 것을 추가**하거나 **사용 규칙을 정하는** 보완이다.

| # | 문제 | 보완안 | 상태 |
|---|---|---|---|
| T-1 | **한글 글꼴 없음.** 밝은 모드는 `Inter`, 어두운 모드는 `Segoe UI` 계열로 서로 다르고, 둘 다 한글 글리프가 없어 OS 기본 한글 글꼴(맑은 고딕, Apple SD 산돌고딕)로 대체된다. 모드 전환 시 글꼴이 바뀐다. | 두 모드 모두 `--font-sans: "Pretendard Variable", Pretendard, Inter, -apple-system, "Segoe UI", sans-serif`로 통일. Pretendard는 한글·영문 모두 지원하고 Inter와 영문 형태가 비슷하다. 웹폰트는 다이나믹 서브셋으로 필요한 글자만 로드. | **[확정] D-044** (2026-11-01) |
| T-2 | **기본색을 글자색으로 쓰면 명암비 부족.** 하늘색 `primary`를 흰 배경 위 링크·강조 글자로 쓰면 약 3:1로 본문 기준(4.5:1)에 못 미친다. | 글자로 쓰는 강조색은 `accent-foreground` 값을 쓰는 `--link` 토큰을 추가. `primary`는 버튼 배경·선택 표시·진행 막대·포커스 링에만 쓴다. | [제안] |
| T-3 | **destructive(빨강) 위 흰 글자 명암비 경계.** 작은 글자에서 4.5:1에 못 미칠 수 있다. | 구현 시 실측. 부족하면 삭제 버튼은 `destructive` 배경 대신 "빨간 글자 + 테두리" 형태(outline destructive)를 기본으로 하고, Alert Dialog의 최종 확인 버튼만 채움 형태로 쓴다. 빨간 글자에는 더 짙은 `--destructive-text` 토큰을 추가. | [검증 필요] |
| T-4 | **성공·경고·정보 색 없음.** 예산 초과, 달성, 해지 예정 같은 상태 표현에 필요. | `--success`, `--warning`, `--info` 토큰 추가(§3.1.3). 테마 색조(청색 계열)와 어울리는 채도로. | [제안] |
| T-5 | **차트 5색이 모두 청색 계열.** 지출 라벨별 원형·막대 차트에서 범주 구분이 어렵다. | 범주 차트는 최대 5개 범주 + `기타`(회색)로 제한하고, 색에 더해 순서·직접 라벨로 구분. 범주가 6개를 넘으면 차트 대신 막대 순위 목록. 추세(단일 계열)에는 `chart-1`. | [제안] |
| T-6 | **목표·트래커 색상이 테마와 별개여야 함.** 사용자 지정 색은 테마가 바뀌어도 유지되어야 한다. | 목표 팔레트를 테마 토큰과 분리된 `--goal-*` 네임스페이스로 정의(§3.1.4). | [확정: 분리 원칙은 ChatGPT 제안을 사용자 맥락에서 유지] [제안: 값] |
| T-7 | **그림자 위주의 층 구분은 밝은 모드에서 카드 경계가 약할 수 있음.** | 카드는 그림자(`shadow-sm`) + `border` 1px을 함께 사용. 목록 행은 그림자 없이 구분선만. | [제안] |
| T-9 | **밝은 모드 포커스 링이 약함**(0단계 실측에서 발견). `ring`(=primary)과 배경의 명암비 2.84:1로 비텍스트 기준 3:1 미달. shadcn 기본은 `outline-ring/50`(반투명)이라 더 약하다. | 포커스 링은 반투명을 쓰지 않고 `ring` 원색 2px + 오프셋 2px. 밝은 모드에서는 링 색을 `accent-foreground` 계열로 진하게 하는 `--focus-ring` 토큰 추가 검토 | [검증 필요] |
| T-8 | **기본 모서리 6px이 펫·포스터 같은 친근한 요소와 대비됨.** | 일반 UI는 테마 모서리 유지. 포스터 썸네일·펫 말풍선·사진은 `--radius-xl`(10px) 사용 허용. | [제안] |

### 2.3 명암비 실측 결과 (0단계 V-02, 2026-11-01)

테마 점검 페이지(`/dev/theme`)에서 브라우저가 실제로 그린 색으로 WCAG 명암비를 측정했다.

| 조합 | 쓰임 | 밝은 모드 | 어두운 모드 | 기준 |
|---|---|---|---|---|
| foreground / background | 본문 | 17.54 ✓ | 16.78 ✓ | 4.5 |
| muted-foreground / background | 보조 글자 | 6.30 ✓ | 6.78 ✓ | 4.5 |
| card-foreground / card | 카드 글자 | 18.05 ✓ | 15.32 ✓ | 4.5 |
| primary-foreground / primary | 기본 버튼 글자 | 6.64 ✓ | 9.59 ✓ | 4.5 |
| **primary / background** | 기본색을 글자로 (T-2) | **2.84 ✗** | 9.57 ✓ | 4.5 |
| accent-foreground / background | `--link` 대안 (T-2) | 13.03 ✓ | 12.38 ✓ | 4.5 |
| secondary-foreground / secondary | 보조 버튼 | 11.69 ✓ | 11.90 ✓ | 4.5 |
| **destructive-foreground / destructive** | 빨간 버튼 흰 글자 (T-3) | **4.05 ✗** | **3.19 ✗** | 4.5 |
| **destructive / background** | 빨간 글자 (T-3) | **3.93 ✗** | 6.07 ✓ | 4.5 |
| **ring / background** | 포커스 링 (T-9) | **2.84 ✗** | 9.57 ✓ | 3 |

결론:
- T-2 확인: 밝은 모드에서 기본색(하늘색)을 글자로 쓰면 안 된다. 링크·강조 글자는 `--link`(= accent-foreground)를 쓴다. 이 프로젝트의 shadcn 스타일(radix-nova)의 `link` 버튼 변형이 기본색 글자를 쓰므로 `--link`로 바꿔야 한다.
- T-3 확인: 빨간 버튼 위 흰 글자는 두 모드 모두 미달. 빨간 글자는 밝은 모드에서 미달. → `--destructive-text` 토큰 추가, 최종 확인 버튼은 글자를 굵게(600)·크게(16px) 하거나 배경을 더 진하게 조정.
- T-9 새로 발견: 밝은 모드 포커스 링 보강 필요.
- 글꼴: 두 모드 모두 Pretendard로 표시됨(D-044 확인).

#### 3.1.3 상태 색 사용 규칙 [제안]

| 상태 | 표현 | 예 |

색만으로 의미를 전달하지 않는다. 항상 글자 또는 아이콘이 함께 간다.

### 6.3 정보 밀도 원칙 [확정: 단순 축소 금지]

- 모바일은 PC 화면을 줄인 것이 아니다. **모바일에서 보이지 않게 되는 정보는 "숨김"이 아니라 "다음 단계로 이동"** 이어야 한다(상세 화면에 반드시 존재).
- 모바일 목록 행은 최대 3가지 값: 제목, 핵심 값(금액·날짜), 상태 1개. 나머지는 상세.
- PC 표는 최대 7열. 그 이상은 열 선택(보기 옵션).

### 6.4 모바일 전용 고려

- 하단 안전 영역(`env(safe-area-inset-bottom)`) 패딩.
- 엄지 영역: 주요 버튼은 화면 하단 1/3에.
- 키보드가 올라오면: 하단 탭·빠른 추가 버튼 숨김, Drawer 저장 버튼은 키보드 위로.
- 스와이프: 목록 행 왼쪽 스와이프 → `삭제` 버튼 노출 [제안], Drawer 아래로 스와이프 → 닫기(입력 중이면 "작성 중인 내용이 사라져요" 확인).
- 길게 누르기: 목록 행 → 추가 작업 Drawer, 트래커 셀 → 메모 편집.
- 뒤로가기(안드로이드): 열린 Drawer·Dialog를 먼저 닫는다(URL 상태 연동).

## 7. 도움말 체계 [확정: 원칙] [제안: 규격]

### 7.1 원칙 (ChatGPT 대화에서 앱 공통 UX 원칙으로 확정)

> **사용자가 지금 결정해야 하는 정보는 보여주고, 결정에 필요한 상세 설명은 바로 옆에서 확인할 수 있게 하되, 학습용 설명은 별도의 가이드로 분리한다.**

| 정보 유형 | 표시 방식 |
|---|---|
| 누구나 이해하는 기능 | 설명 없이 표시 |
| 생소한 용어의 정의 | i 아이콘 + Popover |
| 선택에 영향을 주는 짧은 설명 | 항목 아래 한 줄(Field description) |
| 복잡한 설정 방법 | ? 도움말 + 상세 가이드 |
| 여러 단계의 사용 방법 | 단계별 가이드 모달 |
| 처음 사용할 때만 필요한 안내 | 최초 1회 안내, 이후 다시 보기 제공 |
| 중요한 주의사항 | 해당 작업 위치에 직접 표시 |
| 입력 오류와 해결 방법 | 문제가 생긴 필드 바로 아래 |
| 부가적인 상세 데이터 | 접기·펼치기 또는 상세 화면 |

추가 원칙:
1. 설명보다 직관적인 UI가 먼저다. 설명이 필요하면 먼저 라벨을 바꿀 수 있는지 본다(예: Want/Like/Need → 갖고 싶음/관심/필요).
2. 중요한 정보는 도움말 안에 숨기지 않는다(다음 결제일, 해지 예정일, 예산 초과 금액).
3. 호버에만 의존하지 않는다. PC는 호버+클릭, 모바일은 탭, 키보드는 포커스+Enter/Space.
4. 설정 모달은 값을 바꾸는 곳, 도움말은 이해하는 곳. 긴 설명 때문에 설정 모달이 커지지 않는다.
5. 숙련도에 따라 안내를 줄인다. 처음엔 보이고, 다음부터는 접히되, 다시 볼 경로는 남긴다.

### 7.2 도움말 컴포넌트 규격

| 컴포넌트(내부 이름) | 기반 | 분량 한도 | 열기 | 닫기 |
|---|---|---|---|---|
| `HintText` (필드 아래 한 줄) | Field description | 1줄, 40자 내외 | 항상 보임 | — |
| `InfoTip` (i) | Popover (+PC 호버 열기) | 제목 선택 + 본문 2~5줄(약 150자) + 선택적 `자세히 보기` 링크 | PC: 호버 300ms 지연 또는 클릭 / 터치: 탭 / 키보드: 포커스 후 Enter·Space | 바깥 클릭, Esc, 다시 클릭. 호버로 연 경우 포인터가 버튼·팝오버를 벗어나면 닫힘 |
| `HowToTip` (?) | Popover | 단계 3개 이하, 번호 목록 | 클릭·탭·Enter (호버로 열지 않음: 읽는 데 시간이 필요) | 동일 |
| `GuideDialog` (상세 가이드) | PC Dialog `lg` / 모바일 전체 화면 페이지 | 제한 없음. 목차(Tabs 또는 Accordion), 예제 이미지, 샘플 다운로드 | `자세히 보기`, ? 안의 링크, /help 페이지 | 닫기, Esc. **작업 중인 화면을 잃지 않는다**: PC는 작업 모달 옆에 나란히 열리는 Sheet(오른쪽)로 열 수 있음 |
| `FirstTimeHint` (최초 안내) | Popover(가리키는 위치에 화살표) | 1~2문장 + `알겠어요` | 기능 첫 진입 시 자동 1회 | `알겠어요`(다시 안 뜸), 바깥 탭(다음 방문 때 1회 더) |
| `InlineNotice` (주의사항) | Alert (작은 형태) | 1~2문장 + 행동 버튼 | 항상 보임 | 해결 시 사라짐 |

- i 버튼 위치: 라벨 오른쪽 4px, 16px 아이콘, 히트 영역 32px(모바일 44px). 라벨과 같은 줄.
- 모바일에서 Popover 내용이 5줄을 넘으면 같은 내용을 Drawer로 연다(Popover가 화면을 가리지 않도록).
- 스크린리더: i 버튼 이름은 "<라벨> 설명", Popover는 `aria-describedby`로 라벨과 연결.
- 도움말 문구는 화면 문구와 같은 문구 규칙(§9)을 따른다. 개발 배경·내부 구조 설명 금지.

### 7.3 도움말 콘텐츠 관리 [제안]

- 도움말 문구는 코드에 흩어 두지 않고 `help/<topic>.md`(또는 JSON) 한곳에서 관리해 화면과 가이드가 같은 출처를 쓴다.
- 최초 안내를 본 기록은 사용자 설정(`seen_hints`)에 저장해 기기를 바꿔도 다시 뜨지 않는다. 설정 > 화면 > `안내 다시 보기`로 초기화.

### 7.4 도움말 적용 대상 목록 (초안)

## 9. 문구(UX writing) 규칙

### 9.1 어조 [제안]

- 해요체, 짧고 친근하게. "~합니다" 대신 "~해요".
- 펫 말풍선만 더 귀엽게(이모지 최소 사용). 시스템 문구는 담백하게.
- 사용자를 탓하지 않는다: "잘못 입력했습니다" → "금액을 숫자로 입력해 주세요".

### 9.2 라벨 규칙 [확정: 직관적·간결]

| 규칙 | 예 |
|---|---|
| 명사형 라벨은 2~4글자 우선 | `지출`, `고정 지출`, `예산`, `카드` |
| 버튼은 동사로 끝 | `추가`, `저장`, `해지 예정으로 바꾸기`, `구매함`(상태 전환 버튼은 완료형 허용) |
| 영어·약어 지양 | `Want/Like/Need` → `갖고 싶음/관심/필요`, `Sync` → `새로 가져오기`, `Soft delete` → 사용자에겐 `휴지통` |
| 같은 개념 = 같은 단어 | "삭제"는 휴지통으로 보내기, "영구 삭제"는 되돌릴 수 없는 삭제. "해지"는 고정 지출 종료에만 |
| 숫자 앞 단위 생략 금지 | `13,500원`, `3일 남음`, `12/30일` |

### 9.3 노출 금지 용어 목록 (내부 → 화면)

| 내부 용어 | 화면 문구 |
|---|---|
| soft delete, deleted_at | 휴지통으로 이동 |
| hard delete, purge | 영구 삭제 |
| revision, audit log | 변경 기록, 보안 기록 |
| API log | (노출 안 함) |
| sync token, webhook | (노출 안 함) / "자동으로 가져와요" |
| OAuth, scope | "구글 계정으로 연결", "일정 읽기·쓰기 허용" |
| API key | API 키 (AI 연결 화면에서만, i로 설명) |
| state machine, idle/walk | (노출 안 함) / 펫 동작 이름: 가만히 있기, 걷기, 따라오기, 잠자기, 놀라기, 말하기 |
| tenant, user_id | (노출 안 함) |
| null, undefined, NaN | 빈 값은 `—` 또는 "아직 없어요" |
| HTTP 4xx/5xx 코드 | "잠시 후 다시 시도해 주세요" + 필요 시 `오류 코드 E-1234`(지원 문의용, 작게) |

**사용자가 기능을 요청한 이유나 개발 배경을 UI에 쓰지 않는다.** [확정] 예: 고정 지출 메모 입력란 placeholder에 "넷플릭스 중복 결제 방지용"을 쓰지 않고 "예: 넷플릭스 이용권 포함"처럼 입력 예만 보인다.

### 9.4 형식

| 대상 | 형식 |
|---|---|
| 금액 | `12,000원` (천 단위 쉼표). 큰 금액 요약은 `1.2만원`·`230만원` (위젯에서만) |
| 음수(수입·환불) | `+50,000원` (초록 글자 아님, 기본색 + `+`) |
| 날짜 | 올해: `11월 1일 (일)`, 다른 해: `2025년 11월 1일`. 상대: `오늘`, `어제`, `3일 전`(최근 7일까지) |
| 시간 | `오후 2:00` (모바일), PC도 동일. 24시간제 설정 옵션 [제안] |
