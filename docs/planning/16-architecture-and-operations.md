## 4. 논리 구조

```
[브라우저 / PWA]
  ├─ UI (shadcn) ── TanStack Query ── IndexedDB(캐시·대기열)
  ├─ 펫 레이어(requestAnimationFrame)
  └─ 서비스 워커(셸 캐시, 푸시 수신)
        │ HTTPS (세션 쿠키)
[앱 서버: Next.js]
  ├─ Route Handlers /api/v1 ─┐
  ├─ Server Actions ─────────┼─▶ 서비스 계층(권한·검증·변경 이력·감사 로그)
  ├─ 웹훅 /api/webhooks ─────┘        │
  ├─ AI 오케스트레이터(도구 호출) ──────┤
  └─ 예약 작업 실행기(cron) ───────────┤
                                      ▼
  [PostgreSQL]   [파일 저장소(로컬 폴더): 사진·펫·로그 파일]   [외부: 카카오·네이버·구글·AI 3사·도서/TMDB]
  * 예약 작업 실행기는 별도 worker 프로세스(§5.2). 백업은 PC 밖 두 곳(§7)
```

- **서비스 계층 하나**를 모든 진입점(API, Server Action, AI 도구, 예약 작업)이 공유한다. 권한 검사·soft delete 필터·변경 이력·감사 로그가 빠지는 경로가 없게. [제안]

## 5. 운영 방식: 본인 PC 자가 운영 [확정 D-034]

### 5.1 결정과 그 결과

사용자가 2026-11-01에 **본인 PC 운영**을 골랐다. 이 선택으로 생기는 이점과 감수할 점은 다음과 같다.

| 구분 | 내용 |
|---|---|
| 이점 | 운영 비용이 거의 없다(전기료). 앱이 인터넷에 공개되지 않는다(Tailscale 사설망, D-043). 데이터가 내 PC 안에 있다. "내 구독으로 AI 쓰기" 경로(ChatGPT 계정 로그인)의 조건인 **로컬 호스팅**을 만족한다 [12 §3]. 서버 함수 실행 시간·본문 크기 같은 클라우드 제약이 없다 |
| 감수할 점 | **PC가 꺼지거나 잠들면 앱 전체가 멈춘다**(모바일 접속, 알림, 자동 기록, 캘린더 동기화). 백업·보안 패치·장애 대응을 직접 한다. 바깥에서 쓰는 모든 기기에 Tailscale이 켜져 있어야 한다. 외부 서비스가 보내는 신호(웹훅, 구글 캘린더 푸시)는 받을 수 없다(§5.3) |
| 확장 | 다른 사용자를 받는 3단계에서는 남의 데이터를 집 PC에 두지 않도록 **클라우드 이전을 다시 검토**한다(§5.8). 그때 쉽게 옮길 수 있게 처음부터 컨테이너·Postgres·저장소 인터페이스로 만든다 |

### 5.2 구성 [제안]

```
[본인 Windows 11 PC]
  Docker Desktop (WSL2)
  ├─ app        Next.js (Node.js, standalone 빌드)          ← 화면·API·웹훅
  ├─ worker     같은 코드베이스의 작업 프로세스(pg-boss)       ← 예약 작업·알림 발송·동기화·백업
  ├─ db         PostgreSQL (Docker 볼륨 oona_oona-pg, 127.0.0.1:55440)  ← 외부 포트 열지 않음
  Tailscale (Windows 앱 또는 컨테이너)                       ← tailscale serve 로 app을 HTTPS로 사설망에만 제공
  파일: C:\oona-data\files  (사진·펫·로그 압축 파일·내보내기, D 드라이브 없음 §5.7.1)
  백업: 외장 드라이브 + 클라우드 드라이브(암호화) §7

[휴대폰·노트북 (Tailscale 켬)] ──Tailscale 사설망·HTTPS──▶ https://oona.<tailnet>.ts.net ──▶ app
[app·worker] ──바깥으로 나가는 요청만──▶ 카카오·네이버·구글·AI·검색 API, 웹 푸시 서비스, 가동 확인 서비스
```

- 경로의 드라이브 문자·폴더는 예시다. 데이터 폴더는 프로젝트 폴더(바탕화면)와 분리한다(실수로 지우거나 동기화 앱이 건드리지 않게).
- Docker를 쓰는 이유: 설치·업데이트가 명령 하나로 되고, 개발용과 운영용을 분리하기 쉽고, 나중에 클라우드로 그대로 옮길 수 있다. Docker 없이 Windows 서비스로 직접 실행하는 방법은 대안으로만 둔다.

### 5.3 외부 접속: Tailscale 사설망 [확정 D-043]

사용자가 Tailscale을 골랐다(문서 추천은 Cloudflare Tunnel이었음). 앱은 인터넷에 공개되지 않고, Tailscale에 로그인한 본인 기기에서만 열린다.

**동작하는 것과 바뀌는 것**

| 기능 | 결과 | 처리 |
|---|---|---|
| 휴대폰·노트북 접속 | ✓ Tailscale 앱이 켜져 있으면 어디서나 | iPhone·안드로이드 Tailscale 앱에서 "항상 연결"(VPN On Demand) 설정 [제안] |
| HTTPS·PWA 설치·서비스 워커 | ✓ Tailscale이 발급하는 `*.ts.net` 인증서 사용 | 관리 콘솔에서 MagicDNS·HTTPS 인증서 켜기, `tailscale serve`로 app(3000번)을 443으로 제공 [검증 필요 V-01] |
| 웹 푸시 알림 | ✓ 서버 → 푸시 서비스(FCM·APNs)로 나가는 요청이라 가능 | iOS는 여전히 홈 화면 설치 필요 |
| 카카오·네이버 로그인 | ✓ 예상: 인증 후 돌아오는 주소(`https://oona.<tailnet>.ts.net/...`)는 휴대폰 브라우저가 여는 주소라 사설망에서도 동작. 토큰 교환은 서버가 바깥으로 요청 | 콘솔에 ts.net 주소를 Redirect URL로 등록할 수 있는지 [검증 필요 V-03] |
| 카카오·네이버 **연결 끊기 웹훅** | ✗ 외부에서 들어올 수 없음 | 다음 로그인·토큰 사용 실패 시 연결 끊김으로 처리(13 §4.3). 1인 사용에는 영향 작음 |
| 구글 캘린더 **실시간 푸시(G3)** | ✗ | 주기 동기화(15분) + 앱 열 때 + `지금 가져오기`로 대체(07 §4.2). G1·G2(가져오기·양방향)는 그대로 가능 |
| 네이버 캘린더 보내기·CalDAV, 카카오 톡캘린더 | ✓ 서버가 바깥으로 요청 | |
| AI 3사, 작품 검색, 링크 미리보기 | ✓ | |
| ChatGPT 계정 플랜 사용(12 §3 B) | 로컬 호스팅 조건에 더 잘 맞음(공개 주소 없음) | V-10에서 확인 |
| 서버 꺼짐 감지 | 외부 서비스가 서버를 확인할 수 없음 | **서버가 5분마다 바깥으로 신호를 보내고, 신호가 끊기면 알리는 방식**(하트비트)으로 바꿈 §5.4 |
| 다른 사용자 초대(3단계) | 상대도 내 Tailscale 망에 들어와야 함(기기 공유) | 3단계에서 클라우드 이전과 함께 다시 결정(§5.8) |

- 웹훅·구글 푸시가 꼭 필요해지면 Tailscale Funnel로 **웹훅 경로만** 공개하는 방법이 있다. 지금은 쓰지 않는다 [미결정 Q-164, 추천: 쓰지 않음].
- PC 이름·tailnet 이름을 바꾸면 주소가 바뀐다. 바꾸면 카카오·네이버·구글 콘솔의 Redirect URL과 휴대폰에 설치한 앱을 다시 맞춰야 하므로, PC 이름을 처음에 정해 두고 바꾸지 않는다.
- 서버가 응답하지 않을 때 화면 띠 문구: "서버에 연결할 수 없어요" + `?`(도움말: Tailscale이 켜져 있는지, PC가 켜져 있는지 확인). Tailscale은 사용자가 직접 설치한 앱 이름이라 도움말에서는 그대로 쓴다.
- 보안: 앱이 공개되지 않으므로 무차별 로그인 시도 위험이 크게 줄어든다. 그래도 앱 로그인·요청 제한·세션 보안은 그대로 둔다(다른 기기 분실 대비).

**처음 비교했던 접속 방식 (기록용)**

| 방식 | 공개 HTTPS 주소 | 카카오·네이버 로그인 | 카카오·네이버 연결 끊기 웹훅 | 구글 캘린더 푸시 | 휴대폰 준비 | 보안 |
|---|---|---|---|---|---|---|
| Cloudflare Tunnel + 개인 도메인 (문서 추천이었음) | ✓ 고정 | ✓ | ✓ | ✓ | 없음 | 포트를 열지 않음. 앱 로그인으로 보호 + Cloudflare 요청 제한 규칙 |
| **Tailscale (사설망)** (선택) | 사설망 안에서만 | 대체로 가능(리다이렉트는 브라우저 기준) [검증 필요] | ✗ (외부에서 못 들어옴) | ✗ → 주기 동기화만 | 휴대폰에 Tailscale 앱 상시 연결 | 가장 안전(외부에 아예 안 보임) |
| 공유기 포트 포워딩 | ✓ | ✓ | ✓ | ✓ | 없음 | **비권장**(집 IP 노출, 인증서·DDNS 직접 관리) |

- PWA 설치·서비스 워커·웹 푸시는 **HTTPS가 필수**다. 집 와이파이에서 `http://PC주소:3000`으로 접속하면 앱 설치·알림이 동작하지 않는다. 집에서도 항상 `ts.net` 주소로 접속한다.

### 5.4 PC 상시 가동 [검증 필요 Q-161]

| 항목 | 설정 |
|---|---|
| 절전 | 전원 설정에서 "절전 모드 안 함"(화면 끄기는 괜찮음) |
| 재부팅 후 자동 시작 | Docker Desktop은 기본적으로 **Windows 로그인 후** 시작된다. Windows 업데이트로 재부팅되면 로그인 전까지 앱이 멈춘다 → 해결안 비교: (a) 작업 스케줄러로 부팅 시 WSL2 안의 Docker 엔진 시작(로그인 불필요) (b) Windows 자동 로그인(보안 약화) (c) 재부팅 시간대 지정 + 꺼짐 알림으로 수동 대응. 추천 (a), 0단계에서 검증 |
| 컨테이너 재시작 | 모든 서비스 `restart: unless-stopped` |
| 꺼짐 감지 | 사설망이라 외부에서 서버를 확인할 수 없다. 대신 **worker가 5분마다 하트비트 감시 서비스(무료 등급, 예: Healthchecks.io)로 신호를 보내고**, 신호가 15분 끊기면 그 서비스가 휴대폰으로 "앱 서버가 응답하지 않아요" 알림(메일·푸시 앱) [제안] |
| 정전 | 선택: 소형 UPS. 없으면 전원 복구 시 PC 자동 켜짐(BIOS 설정) |

### 5.5 PC가 꺼져 있던 동안의 처리 [제안]

| 기능 | 꺼져 있는 동안 | 다시 켜졌을 때 |
|---|---|---|
| 휴대폰에서 앱 열기 | 마지막으로 본 화면을 읽기 전용으로 표시(PWA 캐시), 상단 "서버에 연결할 수 없어요" | 자동 재연결 |

| 일정·결제 알림 | 발송 안 됨 | 지난 알림은 푸시로 보내지 않고 알림 센터에 "놓친 알림"으로 모음. 아직 시점이 남은 알림만 정상 발송 |
| 고정 지출 해지 전환·자동 기록 | 실행 안 됨 | 밀린 날짜만큼 따라잡기 실행(작업은 멱등, 날짜별 1회) |

- 화면 문구: 서버가 꺼져 있을 때의 상단 띠는 일반 오프라인과 구분한다. "서버에 연결할 수 없어요 · 최근 데이터를 보여 드려요". [03 §10 확장]

### 5.6 업데이트 [확정: 업데이트가 번거롭지 않게] [제안: 방식]

- **업데이트 명령 하나**: 프로젝트 폴더에서 업데이트 스크립트 실행 → 최신 코드 받기 → 이미지 빌드 → DB 마이그레이션 → 컨테이너 교체 → 상태 확인. 실패하면 이전 이미지로 자동 되돌리기.

| 로그 | 저장 | 보존 | 비고 |
|---|---|---|---|
| API 로그 | DB `api_logs`(일 단위 파티션) → 매일 전날분을 데이터 폴더 `files/logs/api/YYYY/MM/YYYY-MM-DD.jsonl.gz`로 이동 | DB 30일 + 파일 1년 | 필드는 [14 §5.1]. 본인 PC 운영이라 사용자 제안(날짜별 파일)이 그대로 들어맞는다 |
| 감사 로그 | DB `audit_logs` | 1년 + 압축 파일 3년 | 사용자 보안 기록 화면 원천 |
| 앱 오류 로그 | 컨테이너 로그(날짜별 파일, 30일 순환) + 선택적으로 오류 추적 서비스(Sentry 무료 등급 등) | 30~90일 | 개인정보 마스킹 설정 필수 |
| 작업 실행 기록 | DB `job_runs` | 90일 | |

**판단 근거**: 1인 사용 기준 하루 API 요청은 수천 건 수준이라 DB만으로도 충분하지만, 다중 사용자 확장과 장기 보관 비용을 고려해 처음부터 "최근은 DB, 오래된 건 날짜별 압축 파일" 구조로 만든다. 사용자 제안(날짜별 텍스트 파일)을 그대로 살리되 압축 JSON Lines로 용량을 줄이고 검색 도구(jq, DuckDB)로 바로 읽을 수 있게 한다.

마스킹 규칙: 비밀번호·토큰·API 키·쿠키·인증 헤더·건강 값·일기 본문은 어떤 로그에도 남기지 않는다. 쿼리 문자열의 `q`(검색어)도 기본 미기록 [제안].

## 7. 백업·복구 [확정: 포함 요구] [제안: 정책]

| 대상 | 방법 | 주기 | 보관 |
|---|---|---|---|
본인 PC 운영에서는 **PC 디스크 고장·도난·랜섬웨어**가 가장 큰 위험이다. 백업을 같은 디스크에만 두면 백업이 아니다. 백업은 반드시 두 곳 이상(PC 밖 물리 장치 1곳 + PC 밖 원격 1곳)에 둔다(3-2-1 원칙). [제안]

| 대상 | 방법 | 주기 | 보관 위치 | 보관 |
|---|---|---|---|---|
| DB | 논리 덤프(pg_dump, 압축·암호화) | 매일 03:00 + 업데이트 직전 | ① 외장 드라이브 ② 이미 쓰는 클라우드 드라이브(rclone 등으로 암호화 업로드) [확정 D-049] | 일일 30일 + 월말 12개월 |
| DB | WAL 보관(선택, 시점 복구) | 연속 | 외장 드라이브 | 7일 |
| 파일 | 데이터 폴더 증분 복사(사진·펫·로그 압축 파일) | 매일 | ①② 동일 | 30일 + 월말 12개월 |
| 비밀값 | 마스터 암호화 키·`.env` 운영 값 | 변경 시 | 비밀번호 관리자 + 오프라인 사본(본인 보관). **백업 파일과 같은 곳에 두지 않음** | — (키를 잃으면 암호화된 AI 키·건강 값 복구 불가) |

- 백업 파일 자체도 암호화한다(클라우드 드라이브 업체가 내용을 볼 수 없게).
- 클라우드 드라이브 쪽 주의 [제안]:
  - 어떤 서비스인지(OneDrive, Google Drive 등)는 설치 단계에서 사용자가 쓰는 계정으로 정한다. rclone은 둘 다 지원한다.
  - **PC의 동기화 폴더에 백업 파일을 두는 방식은 쓰지 않는다.** 랜섬웨어가 PC 파일을 암호화하면 동기화로 클라우드 사본까지 덮어쓸 수 있다. rclone으로 업로드만 하고, 클라우드 쪽 버전 기록·휴지통 기능을 켜 둔다.
  - 백업 용량(일일 30개 + 월말 12개)이 클라우드 드라이브 여유 공간 안에 드는지 V-13에서 측정한다.
- 외장 드라이브 쪽 주의: 백업할 때만 연결하거나, 상시 연결이면 백업 전용 폴더에 다른 프로그램이 쓰지 못하게 권한을 나눈다(랜섬웨어 대비). [제안]
- 디스크 암호화: Windows 11 Pro의 BitLocker를 데이터 드라이브에 켜는 것을 추천(PC 도난 대비). [제안]
- **복구 리허설**: 분기 1회, 최신 덤프를 개발 환경 빈 DB에 복원 → 행 수·체크섬·샘플 화면 확인 → `purge_ledger` 재적용 → 결과 기록. [14 §6]
- 목표: RPO 24시간(WAL 보관 시 수 분), RTO 4시간(같은 PC) / 1일(새 PC에 Docker 설치 후 복원).
- 새 PC 복원 절차를 문서(운영 메모)로 남긴다: Docker 설치 → 프로젝트 받기 → `.env` 복원 → DB 덤프 복원 → 파일 폴더 복원 → Tailscale 로그인(같은 PC 이름으로 주소 유지) → `tailscale serve` 설정.
- 사용자 단위 복구: 휴지통·변경 기록으로 해결(백업 복원은 전체 장애용).
- 내보내기(사용자용): JSON·CSV + 파일 ZIP. 다른 곳으로 옮기거나 개인 백업용.

| 외부 요청 | 링크 미리보기·CalDAV는 SSRF 방지(사설 IP 차단, 리다이렉트 제한) |
| 업로드 | 형식 실제 검사, 이미지 재인코딩(악성 메타데이터 제거), ZIP 압축 폭탄 방지(풀린 크기·파일 수 제한) |
| 관리자 | 운영 화면은 별도 경로 + 2단계 인증, 사용자 데이터 열람 기능 없음 |
| 사고 대응 | 키 유출 시 교체·세션 전체 폐기 절차, 사용자 알림 문구 준비 |

## 10. 비용 [검증 필요]

| 항목 | 예상 |
|---|---|

| 선택 | UPS, 외장 드라이브 |

## 11. 개발·배포 흐름 [제안]

| 환경 | 용도 | 데이터 |
|---|---|---|
| 개발 | 같은 PC, localhost | 시드 데이터(가짜) |
| 운영 | 같은 PC, ts.net 주소 | 실제 데이터 |

- 흐름: 작업 브랜치 → 검사(타입·린트·단위·E2E·교차 사용자 접근 테스트·접근성, 로컬 또는 GitHub Actions) → main 병합 → 업데이트 스크립트로 운영 반영(§5.6) → DB 마이그레이션(뒤로 호환되는 순서: 열 추가 → 코드 배포 → 옛 열 제거).
- 운영 반영 직전 자동 DB 덤프(되돌리기용).

## 12. 관측 [제안]

| 지표 | 목표·경보 |
|---|---|
| API 오류율 | 5분간 5xx 2% 초과 시 알림 |
| 응답 시간 | p95 500ms |
